# How husk_sdk works

husk_sdk never decides at generation time whether the vendor SDK is there.
`generate` writes build logic that decides **when the native build runs**,
on whatever machine runs it. The same committed files therefore build:

- on a contributor's laptop or a fork's CI, without the binary: the stub;
- on a release machine that has the binary: the real SDK.

The binary itself is never committed. It reaches the build in one of three
ways, checked in this order:

| | iOS, SwiftPM | iOS, CocoaPods | Android (Gradle) |
|---|---|---|---|
| 1 | | | Gradle property `acmeWidgetSdkDir` (`-P`, `gradle.properties`) |
| 2 | environment variable `ACME_WIDGET_SDK_DIR` | | environment variable `ACME_WIDGET_SDK_DIR` |
| 3 | `ios/<plugin>/husk_vendor/` | `ios/<plugin>/husk_vendor/` | `android/husk_vendor/` |

CocoaPods only looks in `husk_vendor/`: Flutter reaches plugin pods
through `.symlinks`, and a path that climbs out of a symlinked pod root
with `..` means one place to CocoaPods and another to the compiler (see
[traps](traps.md)). `link` reads `$ACME_WIDGET_SDK_DIR`, so
`dart run husk_sdk link` covers the CocoaPods case.

`husk_vendor/` folders are filled by `dart run husk_sdk link` and are
git-ignored by a block `generate` adds to `.gitignore` (and `.pubignore`
when the package has one). Names above are the defaults derived from
`sdk.name: AcmeWidgetSDK`; all of them can be set in `husk.yaml`.
`HUSK_SDK_DISABLE=1` forces the stub everywhere, which is handy for
checking that the stub path still compiles on a machine that has the SDK.

## The pieces `generate` writes

There are two kinds of output:

- **Owned files** start with `// GENERATED by husk_sdk`. `generate`
  rewrites them completely and refuses to overwrite a file at the same path
  that lacks the header (unless `--force`).
- **Managed blocks** live inside files the project owns (`Package.swift`,
  the podspec, `build.gradle(.kts)`, `.gitignore`). They sit between a
  `BEGIN husk_sdk` and an `END husk_sdk` comment; only the lines between the
  markers are ever touched. A missing block is inserted once: at the end of
  `Package.swift`, Gradle files and ignore files, and before the closing
  `end` of the podspec.

### iOS, Swift Package Manager

Flutter builds plugins as Swift packages when Swift Package Manager support
is on. A `Package.swift` is Swift code that runs when the package graph is
resolved, and `PackageDescription` exposes `Context.packageDirectory` and
`Context.environment` to it. The block husk_sdk appends after
`let package = Package(...)`:

1. imports Foundation and looks for `AcmeWidgetSDK.xcframework/Info.plist`
   in `$ACME_WIDGET_SDK_DIR`, then in `husk_vendor/`;
2. turns the hit into a path relative to the package root, because
   `binaryTarget(path:)` rejects absolute paths;
3. appends a target `AcmeWidgetSDKHusk` (sources in
   `Sources/AcmeWidgetSDKHusk/`, generated), plus, when the xcframework was
   found, `.binaryTarget(name: "AcmeWidgetSDK", path: ...)` and a
   dependency of the shim on it;
4. adds the shim (and the binary target, when found) to the plugin's own
   target's dependencies and defines the Swift compilation condition
   `HUSK_ACMEWIDGETSDK` on both targets when found.

`Package` and `Target` are reference types with mutable `targets`,
`dependencies` and `swiftSettings`, which is what lets one block extend a
manifest written by `flutter create` without rewriting it.

### iOS, CocoaPods

A podspec is Ruby evaluated by `pod install`. The block inserted before its
closing `end` checks `husk_vendor/` with `File.exist?`, appends the shim
sources to `s.source_files`, and, when found, sets `s.vendored_frameworks`
and adds `HUSK_ACMEWIDGETSDK` to `SWIFT_ACTIVE_COMPILATION_CONDITIONS` in
`s.pod_target_xcconfig`. CocoaPods compiles the shim into the plugin pod's
own module, so the generated channel handler imports the shim module only
`#if canImport(AcmeWidgetSDKHusk)`, which is true under SwiftPM alone.

### Android, Gradle

`android/husk.gradle` is a Groovy script that the module's build file
applies (`apply(from = "husk.gradle")` in Kotlin DSL, `apply from:` in
Groovy). At configuration time it reads the Gradle property and environment
variable through `providers`, lists the candidate directories, and picks the
last file (by name) matching the AAR glob, e.g. `acme-widget-*.aar`.

- **Found:** the AAR's directory is added as a `flatDir` repository to
  every project, and the plugin depends on it as a module
  (`implementation(name: 'acme-widget-3.2.0', ext: 'aar')`). A plain
  `implementation files('x.aar')` is not used: the Android Gradle Plugin
  refuses direct local AAR dependencies in a library's `bundle*Aar` task,
  which Flutter runs for every plugin. The repository goes to every project
  because the app resolves the plugin's dependencies.
- **Not found:** no dependency is added.

Kotlin has no conditional compilation, so the switch is a source set:
the script adds `src/husk/linked/kotlin` or `src/husk/stub/kotlin` to the
`main` source set. Each holds a generated `AcmeWidgetSDKHusk` object with
`IS_AVAILABLE = true` or `false`. Put code that calls the vendor API in
`linked/` and a twin with the same signatures in `stub/`; the example's
`AcmeGreeter` shows the pattern.

With `android.maven` in `husk.yaml` instead of `android.aar`, the script
links `group:artifact:version` from a repository whose URL comes from a
Gradle property or an environment variable (plus optional credential
properties), and builds the stub when no URL is set.

### Dart

`lib/src/<sdk>_husk.g.dart` holds a class (`AcmeWidgetSdkHusk`) with
`isAvailable()`. It calls `status` on the method channel
`<plugin>/husk`. The generated Swift (`AcmeWidgetSDKHuskChannel`) and
Kotlin (`AcmeWidgetSDKHuskChannel`) handlers answer with
`{available, platform, sdk}`, taken from the shim, so the answer is always
what the native build actually linked. Platforms without a handler
(web, desktop, unit tests without a mock) answer `false`. The answer is
cached for the life of the process; `resetForTesting()` clears it.

The one manual step is registering the handler in the plugin class:

```swift
AcmeWidgetSDKHuskChannel.register(with: registrar)          // iOS, register(with:)
```

```kotlin
AcmeWidgetSDKHuskChannel.attach(binding.binaryMessenger)    // Android, onAttachedToEngine
AcmeWidgetSDKHuskChannel.detach(binding.binaryMessenger)    // Android, onDetachedFromEngine
```

`doctor` and `check` look for these calls.

## Determinism and idempotency

- Output depends only on `husk.yaml` and, for defaults, the plugin's
  pubspec name and Gradle `namespace`. There are no timestamps, absolute
  paths or host-specific values in generated files.
- Files are written only when their content changes, so a no-op
  `generate` leaves modification times (and incremental native builds)
  alone. `check` runs the same plan as a dry run and fails on any
  difference.
- Generated text always uses `\n`. A file that already uses `\r\n` (for
  example a Windows checkout with `core.autocrlf`) keeps `\r\n`.
- Rewriting an existing file truncates it in place, so its permission bits
  are kept; new files get the process umask.

## Values that end up in code

Every `husk.yaml` value is interpolated into Swift, Ruby, Groovy, Kotlin or
Dart source. The spec parser accepts only identifiers, version strings,
channel names, Gradle property names, Maven coordinates and relative paths
made of `[A-Za-z0-9_./+-]`, rejects unknown keys, absolute paths, drive
letters and `..` segments that leave the project, and treats `\` in paths
as a separator, so a spec written on Windows works everywhere.

## `link`, `doctor` and `check`

`link` copies the xcframework (recreating symbolic links on macOS and Linux;
copying their targets on Windows, where creating links needs extra
privileges) and the newest matching AAR into the `husk_vendor/` folders.
Each copy goes to a temporary sibling first and is renamed into place, so
an interrupted copy never leaves half a framework for the next build.

`doctor` and `check` share one report:

- **xcframework:** slices from `Info.plist` (identifier, platform, variant,
  architectures), the framework's `CFBundleShortVersionString` (XML or
  binary property lists), and whether each binary is a static archive or a
  dynamic library (read from the `ar` / Mach-O header, looking through a
  universal wrapper). A missing device or simulator slice is an error; a
  simulator slice without arm64 is a warning.
- **AAR:** `AndroidManifest.xml` package, `versionName`, `minSdkVersion`,
  `classes.jar`, and ABIs under `jni/`.
- **Version:** compared with `sdk.version` when both are known.
- **Generated files:** up to date, out of date or missing.
- **Wiring:** the channel registration calls above.
- **Git:** vendor binaries tracked anywhere in the project.

`doctor` prints everything and exits 0. `check` prints warnings and errors
and exits 1 on any error; `--require-sdk ios` / `android` turns a missing
binary into an error for pipelines that must ship the real SDK. A
malformed command line or `husk.yaml` exits 2.
